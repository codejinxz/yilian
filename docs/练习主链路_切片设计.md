### 3.1 `GET /api/practice/next`

- 参数（全部可选，D7）：`bankId`、`mode`（CLOZE/FREE）、`tag`、`sentenceId`（指定句重练）、`errors=1`（只在错题取题）、`excludeIds`（逗号分隔，≤50 个，并入 `excludeSentenceId`）。
- 取题顺序（与 `engine.pickNext` 逐条对齐）：
  1. `sentenceId` 命中且可访问且 PUBLISHED → 返回 `selection = 卡存在 ? "MANUAL" : "NEW"`（忽略 bankId/tag/exclude；找不到退回常规取题）。
  2. `errors=1`：错题口径（§3.5）过滤 + `bankId/tag/excludeIds` 生效、**mode 不过滤**，按 `due_at` 升序取第一行；`selection="DUE"`。
  3. 到期召回：`reviews WHERE user_id=? AND state='LEARNING' AND due_at<=NOW()` 按 `due_at` 升序，逐张检查 tag/mode（mode 比较卡上的 `mode` 列）/exclude/句子可练（PUBLISHED、题库 PUBLISHED 未删）→ `selection="DUE"`。
  4. 新题：可见句子按 `id` 升序（ULID 单调 ≈ 录入序），跳过「有卡且 state≠NEW」与 exclude/tag 命中者 → `selection="NEW"`。
  5. 无题：`data=null`，HTTP 200。
- 响应：`{ sentence: SentenceView, review: ReviewView|null, selection }`（`sentence` 复用 content `SentenceDetail` 非 tombstone 形状）。
- 错误：`40100`、`40401`、`40000`（mode 非法）、`50000`。
- 排除集合用 SQL `NOT IN`（≤50），先查卡再过滤句子；两次查询，不追求单 SQL。

### 3.2 `POST /api/practice/attempts`

请求（同 API §6.2；`hintsUsed/durationMs/retryOfId` 前端必发，服务端校验同本地 `attemptRequestSchema`）：

- 校验顺序（对齐 `engine.submitLocalAttempt` + mock）：
  1. Bean Validation：`attemptId` UUID、`mode/kind` 枚举、`hintsUsed 0–3`、`durationMs 0–86400000`、`answer.schemaVersion=1`、`answer.mode==mode` → `40000`。
  2. `kind=REVEAL` 时 `answer.revealed==true` → 否则 `40000`；`kind=REVEAL` 时 `slots` 必须为空。
  3. `kind=RETRY`：`retryOfId` 必填且存在同 `user_id`+`sentence_id`+`mode` 的 attempt → 否则 `40000`。
  4. 句子校验：存在、未删、PUBLISHED、题库 PUBLISHED 未删可访问；`sentenceVersionId` 必须 == 当前 `current_version_id`（mock 语义：「题目版本不匹配，请刷新后重试」`40000`）→ 不满足 `40402`。
- **幂等（先查后插 + 唯一约束兜底）**：
  - `answer_hash = SHA-256(规范化 JSON{sentenceId, sentenceVersionId, mode, kind, retryOfId, answer, hintsUsed})`，规范化 = 键排序、无空白、UTF-8；`durationMs`/`clientCreatedAt` 不参与（仅诊断）。
  - 已存在同 `id`：同 `user_id` + 同 `answer_hash` → 用已有 attempt + 最新 grading + 当前 review 重建响应，`replayed=true`（200）。不同 `user_id` 或不同 `answer_hash` → `40903`。
  - 并发：捕获 `DuplicateKeyException` 后回查重放；不引入 `idempotency_record`（DATA-MODEL D-018）。
- 判分：`grading/` 纯函数（§3.3），`grader=LOCAL`、`normalizerVersion="norm-1"`、`rubricVersion="rubric-1"`。
- 排程：§3.6；`kind=RETRY` 完全不动卡；`FIRST`/无 FIRST 的 `REVEAL` 写 `reviews` + `review_logs`（`uk_review_log_attempt` 保一次）。
- 事务：插入 attempts + attempt_gradings + reviews + review_logs 同一 `@Transactional`。
- 响应：API §6.2 全字段；`review.rating` 取本次派生 rating（本地引擎同形）；`nextAction.retryRequired = score!=null && score<100 && kind=FIRST`；`nextAction.canReveal = kind!=REVEAL`。
- 错误：`40000`、`40001`、`40100`、`40402`、`40903`、`42900`（限流见 Q6）、`50000`。

### 3.3 判分规则（norm-1 / rubric-1，与 `grading.ts` 逐条对齐）

**归一化 `Norm1Normalizer.normalize(String): String`**（顺序敏感，逐步实现并移植 `grading.test.ts` 的 14 个用例做 golden 测试）：

1. `String.normalize("NFKC")`；
2. `\u2018\u2019\u201b\u2032 → "'"`；`\u201c\u201d\u201f\u2033 → '"'`；`\u3000 → 空格`；
3. 全角区 `U+FF01–U+FF5E` 逐字符减 `0xFEE0` 转半角；
4. `toLowerCase(Locale.ROOT)`；`\s+ → " "`；`strip()`；
5. 去句末标点：先 `([.!?。！？]+)(["']?)$ → $2`，再去一次 `[.!?,;:。！？，、；：…]+$`，再 `strip()`。

`tokenize(value)` = normalize 后按单空格切分；空串 → `[]`。

**填空 `gradeCloze(zh, chunks, blank, answers)`**：对 `blank` 每个位置（顺序即题号）：

- `expected` = 该语块 `answers` 去归一化空项；`canonical = expected[0]`；`tag` = `chunk.tag` 空则 `"未分类"`；
- 整块命中 `wholeHit` = 输入归一化非空且等于任一 `normalize(answer)`；
- 未整块命中时按 `canonical` 的 token 序逐位比对得 `matched`；`score = round(Σmatched / Σtoken(canonical) × 100)`；
- 批注 `key="slot:"+chunkIndex`、`expected/received` 用原文、`message` = 空→「未填写」，否则 `{tag}错误`（tag 已以「错误」结尾则不重复）、`minimalFix` = 未命中时 `canonical`；
- `summary`：无槽→「没有需要判定的语块」；`missed=0`→「全部命中」；否则「还差 N 处」。

**整句 `gradeFree(zh, ref, text)`**：归一化相等→100；否则 ref token 的多重集覆盖（命中即从池中移除）计 `hitCount`，`score=round(hit/total×100)`；未空且不精确时批注 `key="free:0"`、`tag="整句"`、`message="与参考译文有差异"`、`minimalFix=ref`；`summary`：精确「全部命中」/空「未作答」/否则「要点覆盖 N%」。

**路由**（与引擎 `gradeAttempt` 一致）：`kind=REVEAL` → REVEAL 判分（`score=null`、`hitCount=0`、`totalCount=Σ token(各挖空语块 answers[0])`、`annotations=[]`、`summary="已看答案，记为学习中"`）；否则 `answer.text != null && sentence.blank.length==0` → `gradeFree`；其余 → `gradeCloze`（`slots` 按 `chunkIndex` 映射，缺槽按空串）。

### 3.5 错题 / 复习队列 / 重置 / 今日

**`GET /api/practice/wrong-questions`**（`page,size,includeDisputed,bankId,tag`；引擎口径）：

### 4.4 commit / rollback

- commit：`COMMITTING`（乐观兜底）→ 单 `@Transactional`：对每条 VALID 行——`sentence_versions` 插入（`version_no=1`、`content_hash`、`schema_version=1`、`import_batch_id`）、`sentences` 插入（`IdUtils.newUlid()`、`fingerprint`、`status=PUBLISHED`、`current_version_id` 同事务回填）、**`bank.version += 1` 逐题取用**（§4.5）、row 置 IMPORTED + 回写 `sentence_id/sentence_version_id`；batch COMMITTED + `importedRows/committedAt`；`@OperationLog(module="content", action="IMPORT_COMMIT", reason 可选)`。
  - 指纹冲突在 commit 时由唯一索引兜底 → 捕获转 `40904`（批次 FAILED）。
- rollback：仅 COMMITTED；行级 `sentence.status=RECYCLED, deleted_at=now, deleted_by`，`bank.version+=1` 逐题（tombstone 下发，不硬删、不级联）；batch ROLLED_BACK；`@OperationLog(... action="IMPORT_ROLLBACK", reason 必填)`。

### 4.5 banks P1×2 修复（本块一并交付）

- **P1-1 版本游标同版本跨页丢题**：根因——`findChangedSince` 按 `version > sinceVersion ORDER BY version,id LIMIT n` 分页，而 commit 把同一批题目打同一 `version`，页边界切断同版本组后 `nextSinceVersion` 跳过剩余行。**推荐修复：逐题递增**——commit/rollback 中每处理一行 `bank.version+=1` 并赋给该行 `sentences.version`（事务内天然连续；mock 即此语义），游标永不重版本分组，**零契约变更**、`findChangedSince` 不动。替代方案 `(version,id)` keyset 需要把 API `nextSinceVersion` 改复合游标（契约变更 + 前端同步改造），不推荐（Q3 确认）。配套：API.md §5.5 / DATA-MODEL §5.4 改为「每题递增新银行修订号」；回归测试「导入 200 行 → limit=50 拉满 4 页无丢行」。

## 5. 前端切换方案

### 5.1 `LOCAL_ROUTE_GROUPS`：从「静态开关」到「按登录态开关」

现状：`web/src/lib/api.ts` 的 `LOCAL_ROUTE_GROUPS` 对**所有访客**（含已登录用户）把 `/practice`、`/analytics` 拦到本地引擎；注释宣称「改 enabled=false 整体切回」，但那会让**游客**的练习请求打到服务端 401。切换方案：

1. 表项加语义：`{ prefix: "/practice", mode: "guest" }` / `{ prefix: "/analytics", mode: "guest" }`；`isLocalRouteEnabled(path)` 在 `mode==="guest"` 时要求「当前未登录」。
2. 登录态探针：仿照 `setUnauthorizedHandler`，新增 `setAuthStateProbe(probe: () => boolean)`（router 启动时注入；返回「会话已确认处于登录态」）。`getAccessToken()!=null` 直接视为登录；未持 token 时看 probe（router 的 `me()` 冷启动结果）。探针未就绪按游客处理（本地应答），登录态确认后由 router 失效 practice/analytics Query 重取服务端数据——最坏情况是登录用户的首屏练习数据先写本地 IndexedDB 再切服务端，无破坏性（本地数据保留，见 5.2）。
3. mock 优先级不变（`isMockEnabled()` 仍最优先）；IndexedDB 不可用时维持现行为（走网络）。
4. **验收红线**：切换后游客全链路（定级→练习→错题→统计）必须仍为纯本地、零网络写请求；登录用户同一页面请求出现在服务端日志。

### 5.2 登录用户本地数据迁移：guest-upgrade（推荐）+ 本地数据保留

- **决策**：实现 §3.9 guest-upgrade 全链路（服务端 + 注册后一次性调用），理由：切换后「游客练了 N 天 → 注册」若不迁移，等于「练了全白练」，是主路径体验断裂；契约已定（§4.8），实现复用 attempts 核心逻辑，边际成本低。
- 前端：注册成功（`api.register` 返回）→ 读取本地 `StoredAttempt[].request`（`clientCreatedAt` 升序，≤100 条/批，超出分批）→ 调 guest-upgrade → 全部成功后写 `localStorage["yilian.guest-upgraded.v1"]=deviceId` 标记，不再重发；失败（40903/网络）静默保留本地数据并在设置页提示「部分本地记录未同步，可重试」。设置页增加「同步本地记录到账号」手动入口复用同一函数。
- **本地数据不清理**：IndexedDB 记录保留（可导出/可重置），不做「迁移即删」；避免误删与申诉追溯需求。游客→登录后本地练习引擎不再被路由命中（5.1），数据自然冻结。
- 登录话术（§1.3 捎带项）与此对齐：「注册后本机练习记录会并入账号；原始记录仍保留在本机」。

### 5.3 直连引擎调用点清单（`LOCAL_ROUTE_GROUPS` 覆盖不到的部分）

| # | 决策点 | 推荐 | 影响 |
